## 3 · THE MIGRATION RULE, WHICH COST TODAY

**Never wrap a migration in `begin`/`commit` for the Supabase SQL editor.**

The editor manages its own transaction. A wrapped script reports
"Success. No rows returned" and applies nothing — except that DDL in the
same file DOES commit. Today a single wrapped file created a table and
silently dropped every GRANT in it, with no error either way, and
`has_table_privilege` came back false for all sixteen combinations.

Bare statements only. Verify with `has_table_privilege`, not with
`information_schema.role_table_grants` — the latter returned zero rows for
grants that had genuinely applied.

**A table created by hand in the SQL editor gets no default Supabase
grants.** Every new table needs its `service_role` grant written
explicitly.


Two of those are **untracked** — they exist only in the working tree.
`PROCEDURES-AND-LANES` §5 records that fifteen days of work once existed
only in a working tree and was nearly lost. **Commit them.**

The practice that has kept the two lanes from colliding, stated so it
survives a handoff:

- Check branch state before committing. `git status --short` first.
- Stage by explicit path. Never `git add -A` — it sweeps up the other
  lane's work in progress.
- Commit and push the same day. No exceptions.
- `gh pr create --fill` then `gh pr merge --merge --delete-branch=false`.
  **Never delete the branch.**
- Vercel builds twice per PR — Preview from the branch commit, Production
  from the merge commit on `main`. Production is what customers hit, and
  it only exists after the merge. **A PR that is created but not merged
  ships nothing.**
