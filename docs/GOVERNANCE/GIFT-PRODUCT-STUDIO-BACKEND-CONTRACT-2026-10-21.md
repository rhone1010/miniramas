# Shared Product Studio: what the backend supports for both entrances (CC), 2026-10-21

## Entrance A: newly generated Gift Wizard artwork, SUPPORTED end to end
`POST /sessions` (photo) -> `POST /sessions/{id}/batches` (six previews) -> `POST /sessions/{id}/artwork` (favorite) -> `GET /sessions/{id}/product-preview?productId=` (scene-backed preview, `?provisional=1` for a differently shaped favorite) -> `PUT /sessions/{id}/lines` (cart; server gate below) -> `POST /sessions/{id}/checkout` -> webhook/verify -> `POST /sessions/{id}/compositions` (adaptation, durable job state) -> corrections `POST .../compositions/{lineId}/correct` -> `POST .../compositions/{id}/approve` -> `POST /sessions/{id}/finalize` (approval only). Operator-only: repair, release.

## Entrance B: existing My Collection artwork, NOT supported by the Gift rules today (one genuine gap)
What exists for owned artwork is the Print Shop path: `GET /api/v1/print/source?previewId=` (`ownedPrintSource`: the piece must belong to the user's portfolio, series portraits/pets/groups, a compatible aspect), `/api/v1/print/checkout`, `/api/v1/print/order`. That path is a different pipeline: no composition or aspect adaptation, no corrections, no per-line approval, no Final Approval, no `gift_order` lifecycle, no scene gate. So a Product Studio entered from My Collection cannot follow "the same backend rules" with the existing APIs.

### Gap G1: there was no way to start a Gift session whose favorite is an existing owned piece. BUILT (committed, 057 not yet applied): see GIFT-COLLECTION-ENTRANCE-CONTRACT-2026-10-21.md
Why the existing API cannot do it:
1. `POST /sessions` only accepts a photo and runs a fresh analysis; there is no "from collection" input.
2. A selectable favorite is a `gift_previews` row, which must belong to a `gift_batches` row (`kind in ('free','paid')`, exactly six effect ids, migration 047), so a single imported piece cannot be inserted without a schema change.
3. `gift_finalize_order` (and the old approve) creates the My Collection piece for the favorite by inserting `preview_ledger(id = artwork_preview_id)`: for an owned piece that id already exists, so approval would fail unless the session is created with `unlock_portfolio_id` already set to the owned portfolio (the function skips creation when it is set).
4. Corrections regenerate from the session's source photo: an owned piece has its photo in `portfolios.source_image`, which would have to be copied into the session.

### Proposed contract (not built; needs your go-ahead and Codex 2's confirmation)
`POST /api/v1/gift/sessions/from-collection` body `{ previewId }` (the owned `preview_ledger` id) -> `201 SessionView` with `artworkPreviewId` already set and `batches` empty, `entitlement` showing no free batches needed. Server: verify ownership with `ownedPrintSource`; copy the clean original to the session's master path and a watermarked view to its preview path; copy `portfolios.source_image` to `source_path`; analysis from the stored photo; `series`, `master_aspect` from the piece; create a `kind = 'collection'` batch with one `gift_previews` row `ready`; set `unlock_portfolio_id` to the owned portfolio so finalize creates nothing and the owner's piece is never duplicated or removed by cleanup. After that, everything in Entrance A applies unchanged (preview, cart, gate, checkout, compositions, corrections, approval, finalize).
Needs migration 057 (new batch kind, one effect, `pack_id` rule, a unique "one live collection session per piece" guard) plus store, service, handler, route and tests. Risks to settle first: cleanup/retention must never delete the owned portfolio or its ledger row (the current cleanup code does not touch portfolios, but it has never run against a pre-set `unlock_portfolio_id`); whether a corrected composition for a collection piece should regenerate from the stored photo (same as Entrance A) or be disabled; the Print Shop flow's own checkout stays for existing orders.
Until G1 is built, the Studio's My Collection entrance can show the piece and product options but cannot continue into the Gift cart without a re-upload.

## Server-side sale gate (default ON since this commit)
`GIFT_REQUIRE_APPROVED_SCENE` is now ON unless set to `0`. A configuration with no approved scene is refused at add-to-cart and at checkout (`409 product_not_available`), before any quote or Stripe call, whatever the frontend does. Refused today: all framed, premium and canvas portraits, and everything disabled. Sellable today: every fine art size, premium squares, canvas squares. The two routes carry the scene manifests in their bundle (`next.config.js`, `scene-gate-trace.test.ts` runs the gate against a copy of exactly those files).
